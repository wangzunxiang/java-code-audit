# 审计报告模板与严重度标准

## 严重度判定标准（Rubric）

| 严重度 | 判定 | 典型 |
|:---:|------|------|
| 🔴 严重 CRITICAL | 可被未认证/低权限直接利用，导致系统被控或数据泄露 | RCE/命令注入、不可信反序列化、用户可控 SQL 注入、认证绕过、JNDI 注入 |
| 🟠 高危 HIGH | 需一定条件但危害大 | SSRF、路径遍历、XXE、SpEL/模板注入、敏感数据弱加密(MD5/DES/ECB)、硬编码私钥 |
| 🟡 中危 MEDIUM | 需组合条件或间接危害 | 硬编码口令/令牌、不安全默认配置、输入校验缺失、日志泄露敏感信息 |
| 🟢 低危 LOW | 代码质量/健壮性 | 潜在 NPE、资源未关闭、过时 API、异常吞没 |
| ⚪ 信息 INFO | 提示/疑似误报 | 常量拼接的"SQL 注入"模式命中、测试代码、建议项 |

## 误报处理
- 模式命中 ≠ 漏洞成立。对每条 Critical/High **先读 snippet**：若 sink 数据源是常量/硬编码而非用户输入，降级为 INFO 并写明理由。
- 跨引擎重复（semgrep + findsecbugs 同时命中同一 sink）在 aggregate 阶段按 (文件,行,规则) 去重，保留更高严重度并合并引擎名。

## 报告结构（必须）
1. **结论摘要**：总数 + 各严重度计数表 + 一句优先处置建议
2. **问题明细**：按严重度分组；每条含 `文件:行`、规则 ID、引擎、描述、修复建议、**内联代码片段**
3. **建议修复优先级**：严重→高→中→低，最后建议 CI 门禁
4. **免责声明**：静态分析有漏报/误报，结合单位安全管理制度

## 必须标注的执行说明
- 实际跑了哪些引擎、版本
- 跳过的步骤及原因（如 "SpotBugs 跳过：项目无法编译，无可用 JDK"）
- 目标路径、Java 版本、扫描时间

## 交付物
- `代码审计报告_<YYYY-MM-DD>.md`（自包含，证据内联）
- 可选 `findings.csv`：列 = 严重度, 类型/规则, 文件, 起始行, 结束行, 引擎, 描述, 修复建议, 代码片段
